## 2. 【手法】公式 DLL の「辞書読み出し」を全部見る

前エージェントの積み残しだった「データ読み出しの追跡」を実現した。

### 2.1 なぜ `cpu.mem8` の Proxy では駄目か

v86 の CPU は WASM で動いており、ゲストメモリは wasm 線形メモリへ直接アクセスする。
`cpu.mem8` は遅延生成 Proxy (`v86_emu.js` の `k()` ヘルパ) で、JS 側 API 専用。
CPU のロード/ストアはこれを通らない。また **RAM 内のページに対する `mmap_register` は
wasm CPU に無視される** (実験: RAM 内 0x20000000 にハンドラを付けてもゲストの読み出しで
呼ばれない。1GB 以上の 0x40000000 なら呼ばれる)。

### 2.2 解決策

```
CPU は「RAM 外 (>= memory_size)」の物理アドレス読み書きだけを JS の
memory_map_read8/read32 へ委譲する (mmap_register, 128KB ブロック単位)
```

そこで **辞書イメージを 1GB 以上の 0x40000000 に置いて `mmap_register` でフック** すると、
DLL が辞書のどのバイトを読んだかがすべて観測できる。実装は
`eval/tools/accent_trace.mjs` (`node --no-warnings eval/tools/accent_trace.mjs 十年前`)。

* `Set` でオフセットを重複除去、読み出し時の EIP も記録 (どのコードが読んだか分かる)
* 注意: `v86_emu.set_hook` は Win32 スタブでポート 0xE0.. を使い切るため衝突する。
  空きポート (0xC7) に `OUT` トランポリンを自前で書いてフックした
  (`traceNodes`, ディスパッチャ RVA 0x3bf0 の引数ベクタを記録する)

### 2.3 辞書の全体構造 (確定)

```
0x000000 UNKD (412)        ┐
0x0001a4 POSD (1208)       │ POSD ヘッダ + POS1 (= アクセント結合の品詞クラス表)
  0x0001ac POS1 (1200)     │   +0x18 u16 count = 1182
0x000664 MCGD (36820)      │   +0x1a u8 table[1182] (0x1c6..0x664、MCGD の直前で終わる)
0x009640 MTXD/MTX1         │   +0x08 u16 ペア4組 = (116,189)(51,76)(22,50)(5,10)
0x2b395c MSTD (本体辞書)   ┘
```

## 3. 【最大の成果】アクセント結合アルゴリズムの完全同定

### 3.1 レコードの「extra バイト」= アクセント結合データ (形式確定)

前エージェントは「extra = アクセント結合データらしいが形式不明」で止まっていた。逆アセンブルで確定:

```
record = [pos u16][cost u16][flag u8][moraByte u8][accByte u8][カナ mora バイト]
結合バイト数   = flag & 3
結合バイト位置 = record + 7 + mora + ((flag & 4) ? 3 : 0)
accByte の下位 5bit = accent,  moraByte の下位 5bit = mora
```

各結合バイト `b` の復号 (RVA 0xd265..0xd2c8 のローダ):

```
cls = (b >> 5) - 2          // -2..5
val = (b & 0x1f) + (cls !== 0 ? 20 : 0)   // 0..51
```

* `flag & 4` (0x44/0x45) の長形式は「カナの前に 3 バイト」→ 結合バイトはカナの直後
  (公式ローダの `cmovz ebx,[ebp-0xc]` で確定)
* 前エージェントの `(flag&0x0f)-1` は長さだけが偶然合っていた (意味は誤り)
* **機構も確定**: 「後続語の extra が支配する」の正体は、結合関数が
  「次に付く語」の結合バイトを見るフェーズ 3 である (§3.3)

実例: `ます` = flag 0x41, 結合 1 バイト `0x91` → cls=2, val=37。
公式 DLL のトレースで `[node+0x34] = 37` を実測確認済み。

### 3.2 品詞クラス表 (POS1)

```
[ [dict] + 0x18 ] = u16 count = 1182        (= 全レコードの pos & 0x7fff の総数と一致)
[ [dict] + 0x1a ] = u8  table[1182]
[ [dict] + 0x08 ] = u16 範囲ペア 4 組
```

`dict.pos1` として `core/engine.js` が読む。クラス値は 0..0x44。

### 3.3 結合コード関数 (RVA 0x3770) → 0..49

呼び出し側は `push prev; push next` の順に積むので **arg1 = next, arg2 = prev**
(`[ebp+8] = 最後に push した方`)。前エージェントの「後続語の extra が支配する」はこれ。

```
if (prev.jcnt > 0 && prev.jval[0] in [13,17]) return prev.jval[0]      // フェーズ1
hc = T[posIdx(next)], cp = T[posIdx(prev)], pp = posIdx(prev)
if (hc in [13,24] && (cp in [13,24] || cp == 25)) code = 0x17          // フェーズ2
for i in 0..next.jcnt-1:                                               // フェーズ3
    c = next.jcls[i]
    c==0 -> return next.jval[i]
    c==3 -> if (cp in [10,12] || pp in [51,76]) return next.jval[i]
    c==2 -> if (cp in [31,33] || pp in [22,50] || pp in [5,10]) return next.jval[i]
            if (pp in [116,189]) code = next.jval[i]
    c==4 -> if (pp in [116,189]) return next.jval[i]
    c==1 -> if (cp in [36,67] || cp==69) return next.jval[i]
            if (cp==25 && pp not in [22,50]∪[5,10]∪[116,189]∪[51,76]) return next.jval[i]
    c==5 -> if (cp in [31,33] || cp==25) return next.jval[i]
if (code != 0) return code
if (hc in [31,33] || hc in [10,12]) return 0x30                        // 既定 (RVA 0xca70)
return 0
```

### 3.4 コード → 核位置 (RVA 0x3bf0 の 50 エントリジャンプテーブル, RVA 0x3f74)

`edi` = 句頭からの累積拍数、`esi` = 現在のアクセント句の先頭ノード、`A = [esi+0x40]`。
ハンドラは 30 種ほどで、全部 `core/accent_junction.js` の `applyCode` に移植した。代表例:

| code | 動作 |
|---|---|
| 0,1 | A==0 かつ auxAccent!=0 → A = 累積拍 + auxAccent |
| 2,48 | auxAccent!=0 → 累積拍+auxAccent; でなければ auxMora>3 のとき 累積拍+auxMora-1 |
| 3,37 | A = 累積拍 + 1 |
| 4 | A = (累積拍>2) ? 0 : 累積拍 |
| 5,36 | A = 累積拍 |
| 6,17,47 | A = 0 (平板) |
| 7/8/9/11 | 累積拍が 1/2/2未満/2超 のときだけ 累積拍、他は 0 |
| 10 | 累積拍>2 なら 累積拍+auxAccent、他は 0 |
| 13 | auxAccent!=0 かつ auxAccent!=auxMora なら 累積拍+auxAccent、他は 0 |
| 14 | 同上、他は 累積拍+1 |
| 15,18 | **アクセント句を分割** (マーカー 2 = `/`) |
| 19 | **アクセント句を分割** (マーカー 1 = `+`) |
| 21/22/35 | A = 累積拍-1 / -2 / -1 (A==0 のとき) |
| 24..30,38..45 | A = 累積拍 + k |
| 31 | 累積拍==2 なら A=1、他は A=累積拍 (A!=0 のとき) |
| 46 | A==累積拍 かつ 累積拍>1 → A=0 |

**核位置 A はアクセント句内の拍番号 (1-based)**。A=0 は平板。

### 3.5 核位置の補正 (RVA 0xd0b0) — ン / ッ / ー

公式 DLL の読みは「1 拍 = 1 コード」の配列 (`ジュ` が 1 コード、`ー`/`ッ`/`ン` が各 1 コード)。
描画前に次の補正が入る:

```
A>1 かつ A<=そのノードの拍数 かつ 読み[A-1] が ン / ッ / ー なら A を 1 つ手前へ
```

実測 (公式 DLL のバイト差分実験で確認):

* `十(ジュー a1 m2) + 年` … code 5 で A=2 だが 2 拍目が `ー` → **A=1 → ジュ'ーネン**
* `何(ナン) + 度` … A=2 → `ン` → **A=1 → ナ'ンドモ**
* `すみません(a4 m5) + 、` … A=4 → 4 拍目が `ン` → **A=3 → スミマセ'ン**

これが前エージェントの「同一パラメータで結果が違う」の正体だった。

### 3.6 検証: 公式 DLL のバイト書き換え実験

`eval/tools/official_mut.mjs` で結合バイトを 1 バイト書き換え、出力の階段関数を実測し、
上記の解釈と完全一致することを確認した (十+年, 話し+ます の 2 例 × 40 値以上)。
さらに **ジャンプテーブル自体を書き換える実験**で code→ハンドラの添字対応も確認
(code 15 のエントリを潰すと分割が消える / code 12 のエントリを潰しても挙動が変わらない
= 実測時の code は 12 ではない、など)。

## 4. 【未完成】アクセント句の分割規則 (残り 4 文の根因)

### 4.1 機構は判明

アクセント句の境界は **ディスパッチャの呼び出し側** (RVA 0xcea0) が決める:

1. 事前パス (RVA 0xbc00 → 0xc280) が各語に **「アクセント句境界型」`[node+0x42]`** を与える
   (POS クラス + 文脈から計算。値は 0 / 1 / 2 / 3)
2. その型から `[prev+0x44]` にマーカーを立てる: 型 0 → 0 (境界なし)、型 1,2 → 2 (`/`)、型 3 → 1 (`+`)
3. ディスパッチャ自身もコード 15/18 で 2 (`/`)、19 で 1 (`+`) を追加する
4. 呼び出し側は累積拍が 15 を超えると RVA 0xc5c0 で分割点を探して 2 を立てる

トレースで `[node+0x42]` / `[node+0x44]` を 239 文について実測し、
**境界 = 「その語の境界型 != 0」** であることを確認した。

### 4.2 残り 4 文 (すべて「公式はもっと長くまとめる」)

| 文 | 公式 | 我々 | 根因 |
|---|---|---|---|
| その件については後で話しましょう | `ツイテワゴデ` (平板) | `ツ'イテワ`+`ゴ'デ` | `後` の境界型 = 0 (直前が助詞でも続く) |
| 天気がいい日に散歩するのが好きです | `イ'イヒニ` | `イ'イヒ'ニ` | `日` の境界型 = 0 (形容詞+名詞) |
| この本を読み終わったら貸してください | `ヨミオワ'ッタラ` | `ヨ'ミ`+`オワッタ'ラ` | `終わっ` の境界型 = 0 (連用形+動詞) |
| 彼は英語を勉強し始めたばかりです | `ハジ'メタバカリデス` | `ハジメタバ'カリデス` | `し`・`始め` の境界型 = 0 (名詞+する+動詞) |

いずれも「次語の境界型が 0 なのに我々が句を切っている」ケース。
境界型は POS クラスだけでなく **直前語との組み合わせ・junction データ・

## 7. 証拠に基づく否定的結論 (前エージェント分も含む)

| 仮説 | 判定 |
|---|---|
| extra バイト = 連接コスト | **証偽** (連接は MTX1 にある) |
| extra バイトは疎なルックアップテーブルの索引 | **証偽**。テーブルではなく**ビットフィールド** (cls/val) で、ビット演算と分岐で消費される |
| extra を 1 バイトずつ独立に読めば規則が分かる | **証偽**。次語の val と前接語の POS クラスの組で決まる |
| extra の長さ = `(flag&0x0f)` または `(flag&0x0f)-1` | **証偽 (偶然一致)**。`flag&3` + `(flag&4)?3:0` が正しい |
| 核位置 A は「拍」ではなく「文字」インデックス | **証偽**。読みは 1 拍 = 1 コードの配列で、A は拍番号 |
| ン/ッ/ー の補正は頭語のアクセントクラス依存 (テーブル) | **証偽**。単純な「核が ン/ッ/ー を指したら 1 つ手前」規則 |
| アクセント句の分割はディスパッチャが決める | **証偽 (半分)**。主に呼び出し側の事前パス (RVA 0xbc00) が決める |
| 複合名詞は 2 語まで | **証偽**。連鎖は無制限 |
| 連接行列が無い辞書でも既定のままでよい | **証偽 (バグ)**。`useMatrix` で分岐 (前エージェント修正済み) |
| 連接コストは位置ごとの最良 1 個の DP で足りる | **証偽**。状態 = (位置, 品詞) が必要 |
| アクセント結合データのテーブル本体が未同定 | **今回解決**。テーブルは存在せず、POS1 クラス表 + ジャンプテーブル + ビットフィールドだった |
